Multi-Agent Fundamentals

The vocabulary every multi-agent system is built from: orchestrator, supervisor, worker, shared state — then the four patterns they combine into.

Orchestrator — the workflow's project manager

The orchestrator decides which agent runs, when it runs, what information it receives, and when the process is finished. It owns the flow, not the judgment of whether an answer is good.

Supervisor — the workflow's reviewer

A supervisor assigns tasks and evaluates what comes back: it can ask an agent to retry, decide the next step, or decide the answer is good enough to stop. In small systems the same agent plays both roles; the distinction matters once a system grows past one layer.

OrchestratorSupervisor
FocusWorkflow / routingDecision / quality
Typical question"Whose turn is it?""Is this good enough?"
Can trigger a retry?RarelyYes, that's its job

Worker agent — the specialist

A worker agent does one scoped job: a Research Worker finds information, a SQL Worker queries data, a Writing Worker drafts text. It generally has no visibility into the whole workflow — only its own slice of the shared state.

Shared state — the common notebook

Agents coordinate by reading and writing a common data structure, not by talking to each other directly.

Shared State { user_question, research_results, competitor_results, financial_analysis, final_answer } Research Agent ──writes──→ research_results ──┐ Finance Agent ──writes──→ financial_analysis ─┼─→ Shared State ─→ read by anyone downstream
Common mistake. Two parallel agents writing to the same state key. Without an explicit merge/reducer strategy, the second write usually just clobbers the first — this is the single most common cause of "my parallel agent's output disappeared." Give every branch its own key (tab ⑦ shows the fix).

The four patterns

1. Sequential Researcher → Analyst → Writer (each step needs the previous one's output) 2. Hierarchical Main Supervisor / \ Research Supervisor Tech Supervisor / \ / \ Web Agent News Agent Code Agent DB Agent 4. A hierarchical system is a hospital with department heads under a chief of medicine. The pattern you pick should mirror how the real responsibilities are actually structured — not the other way around.

LangChain vs LangGraph: What, When, Where

They solve different problems and are usually used together, not instead of each other.

LangChain

A library of components: LLM wrappers, prompt templates, retrievers, tool definitions, output parsers. It answers "how do I call this model / this tool / this vector store?"

LangGraph

An orchestration engine built on top of those components: state, nodes, edges, conditional routing, loops, checkpointing. It answers "in what order, under what conditions, do these calls happen?"
NeedUseWhy
One LLM call with a prompt templateLangChain aloneNo branching or state to manage
A linear chain: retrieve → prompt → parseLangChain (LCEL chains)Still strictly linear, no loops or conditional branches
An agent that loops until it has an answerLangGraphNeeds explicit state + conditional edges to decide "keep going vs stop"
Multiple agents, shared state, parallel branchesLangGraphThis is exactly what it was built for
Common mistake. Trying to build loops and conditional retries with plain LangChain chains by nesting Python while loops around .invoke() calls. It works for a demo and becomes unmanageable the moment you need to resume from a failure, inspect intermediate state, or run two branches at once — all things LangGraph gives you for free.

Decision rule

If you can draw your workflow as a straight line with no branches, no loops, and no need to inspect state mid-flight — LangChain chains are enough and simpler. The moment you draw an arrow that loops back, or a diamond that asks "which way next?" — reach for LangGraph. Tabs ⑥–⑦ are that diamond and that loop, in code.

Generative AI vs AI Agents vs Agentic AI vs Multi-Agent Systems

Four terms that get used interchangeably in job posts and shouldn't be.

Generative AI └─ one shot: prompt in → content out, no memory of acting AI Agent (= Generative AI + tools + a loop) └─ "do I need a tool? call it. look at result. decide again." Agentic AI (the umbrella paradigm) └─ systems that plan → act → observe → adapt toward a goal (a single agent is ONE way to be agentic; it is not the only way) Multi-Agent System (= Agentic AI, split across specialists) └─ several agents, each scoped, coordinating through shared state
TermHas memory of its own actions?Can call tools?Plans multi-step?Example
Generative AINoNoNoA chatbot answering one question from training knowledge
AI AgentWithin one runYesYes, aloneA single ReAct agent that searches the web then answers
Agentic AIDepends on designYesYesThe paradigm name — covers both of the rows below it
Multi-Agent SystemPer agent + shared stateYes, per agentYes, distributedA supervisor routing to a research agent, a finance agent, a writer agent
Common mistake. Calling any LLM call with a for loop around it "agentic AI." A loop that just retries the same prompt isn't agency — the system needs to be able to choose its next action based on what it just observed. That choice is the dividing line between a generative pipeline and an agent.

Where multi-agent sits in the progression

Single LLM call→ Single Agent (+ tools)→ Agent + more tools→ Multi-Agent System

Each arrow is a decision, not an upgrade you apply by default — tab ③ is entirely about when the rightmost box actually earns its complexity.

Why Multi-Agent? Limits of a Single Agent

If one agent can do the job, use one agent. This tab is about the point where it can't.

1. The context window is working memory, and working memory has a ceiling

Give one agent 100 documents, competitor sites, financial reports, and a long chat history, and somewhere past the ceiling it starts forgetting earlier instructions, mixing unrelated facts, or silently dropping documents. It doesn't fail loudly — it fails by getting quietly worse.

Small task: [ Instruction + Data + Question ] → Agent → Good Large task: [ Docs + Reports + History + APIs + Instructions + ... ] ↓ context limit ↓ information silently lost

2. One agent, every skill

"Build a market research report" quietly asks one agent to search well, extract well, analyze numbers well, and write well. Those are different skills with different failure modes — a prompt tuned to be a precise extractor is rarely also a persuasive writer.

3. Sequential work doesn't parallelize

Research → analyze → find competitors → check reviews → write, at 20 seconds each, is 100 seconds, even though "find competitors" and "check reviews" don't depend on each other at all.

Sequential (one agent): 20+20+20+20+20 = 100s Parallel (three agents at once): Orchestrator ↓ ┌──────────┼──────────┐ Competitor Customer Financial Agent Agent Agent (each ~20s, running together) └──────────┼──────────┘ ↓ Final Report ≈ 20s + merge, not 60s
Analogy — a company, not a solo founder. A solo founder doing research, finance, and marketing alone works at small scale. Past a certain size, you hire a researcher, a financial analyst, a marketer — each specialized, coordinating through shared documents and a manager who decides who does what next. A multi-agent system is that company, built in code.
Common mistake. Reaching for multi-agent because the task is long, rather than because it's genuinely separable. A 2,000-word report that one coherent agent can write end-to-end doesn't get better by being split into five agents — it gets slower, costlier, and harder to debug. Split along real seams: independent sub-tasks, or distinct skills that conflict when forced into one prompt.

The decision in one line

Use multiple agents when the problem genuinely benefits from specialization, coordination, parallel work, or clear separation of responsibility — not simply because more agents sounds more capable.

LangGraph Basics: State, Node, Edge

Phase B · Building

Three words carry the whole mental model. Everything else in LangGraph is built from them.

State = What do we know? Node = What do we do? Edge = Where do we go next?

State — a TypedDict, the workflow's shared notebook

from typing_extensions import TypedDict

class State(TypedDict):
    product_name: str
    basic_description: str
    features_benefits: str
    marketing_message: str
    final_description: str

TypedDict just declares which keys exist and what type each holds — LangGraph doesn't enforce the types at runtime, but your own functions and your IDE both benefit from the contract.

Node — a function that reads state and returns an update

def generate_basic_description(state: State):
    response = llm.invoke([
        SystemMessage(content="You are a helpful assistant that generates brief product descriptions."),
        HumanMessage(content=f"Write a brief description of '{state['product_name']}'.")
    ])
    return {"basic_description": response.content}  # only the changed key(s)
Common mistake. Returning the entire state dict from a node instead of just the changed keys. It still "works" for a simple sequential graph, but it breaks the moment you add parallel branches or a reducer, because LangGraph can no longer tell what each branch actually changed.

Edge — the route between nodes

workflow.add_edge(START, "basic")      # START is the graph's entry point
workflow.add_edge("basic", "features")  # after "basic" finishes, run "features"
workflow.add_edge("final", END)         # END stops the graph and returns state

Function name vs. node label

A Python function and the node name you register it under don't have to match — this trips people up when reading someone else's graph:

builder.add_node("basic", generate_basic_description) Node Label Function ---------- --------------------------- basic → generate_basic_description features → add_features_benefits marketing → create_marketing_message final → polish_final_description

Building and running a sequential graph

START→basic→features→marketing→final→END 
def build_workflow():
    workflow = StateGraph(State)
    workflow.add_node("basic", generate_basic_description)
    workflow.add_node("features", add_features_benefits)
    workflow.add_node("marketing", create_marketing_message)
    workflow.add_node("final", polish_final_description)

    workflow.add_edge(START, "basic")
    workflow.add_edge("basic", "features")
    workflow.add_edge("features", "marketing")
    workflow.add_edge("marketing", "final")
    workflow.add_edge("final", END)
    return workflow.compile()   # validates the graph, makes it runnable

app = build_workflow()
result = app.invoke({"product_name": "Smart Water Bottle", "basic_description": "",
                      "features_benefits": "", "marketing_message": "", "final_description": ""})

app.invoke() sends the initial state to the first node, merges each returned update into shared state, follows the edge to the next node, and repeats until it reaches END.

Analogy — a relay race with a shared baton. State is the baton (it carries everything learned so far). A node is one runner's leg of the race — they do their part, update what's written on the baton, and hand it off. An edge is the handoff itself: it decides whose leg comes next.

LangGraph Advanced: Branches, Fan-In, Loops

Phase B · Building

Four moves turn a straight line into a real multi-agent graph: fan-out, fan-in, conditional edges, and loops.

Fan-out — one node, many branches

workflow.add_edge("basic", "features")
workflow.add_edge("basic", "audience")
workflow.add_edge("basic", "seo")   # three independent branches start together
basic_description ↓ FAN-OUT ┌──────────────┼──────────────┐ ↓ ↓ ↓ add_features identify_audience generate_seo ↓ ↓ ↓ features audience keywords

Each branch must write to a different state key (features_benefits, target_audience, seo_keywords) — this is the fix for the shared-state collision flagged back in tab ④.

Fan-in — many branches, one merge node

workflow.add_edge("features", "marketing")
workflow.add_edge("audience", "marketing")
workflow.add_edge("seo", "marketing")   # marketing only runs once ALL three finish

The merge node (marketing) reads all three results out of shared state — that's the whole point of having a shared notebook instead of three separate conversations.

Conditional edges — the graph makes a choice

workflow.add_conditional_edges(
    "evaluate",
    lambda state: "improve" if state["quality_score"] < 6 else "end",
    {"improve": "improve", "end": END}
)

A normal edge always goes the same way. A conditional edge runs a routing function against the current state and returns a route name, which the route-map dictionary turns into an actual node (or END).

Loops — the graph returns to an earlier node

workflow.add_edge("improve", "evaluate")   # creates: evaluate → improve → evaluate → ...
FAN-OUT Quality Check ┌──────────┼──────────┐ / \ ↓ ↓ ↓ Good Poor Features Audience SEO ↓ ↓ └──────────┼──────────┘ END Improve FAN-IN ↓ ↓ Quality Check (loop back) Quality Check
Common mistake. A loop with no exit guard. evaluate → improve → evaluate is fine until the quality score never crosses the threshold — then it loops forever (or until you hit a provider timeout and a surprise bill). Production loops need a max-iteration counter in state, checked alongside the quality condition — tab ⑨ covers this as a named failure mode.

Reading a full advanced graph definition

def build_workflow():
    workflow = StateGraph(State)
    for label, fn in [("basic", generate_basic_description), ("features", add_features),
                       ("audience", identify_audience), ("seo", generate_seo_keywords),
                       ("marketing", create_marketing_message), ("final", polish_final_description),
                       ("evaluate", evaluate_quality), ("improve", improve_description)]:
        workflow.add_node(label, fn)

    workflow.add_edge(START, "basic")
    for branch in ["features", "audience", "seo"]:        # fan-out
        workflow.add_edge("basic", branch)
        workflow.add_edge(branch, "marketing")              # fan-in
    workflow.add_edge("marketing", "final")
    workflow.add_edge("final", "evaluate")
    workflow.add_conditional_edges("evaluate",
        lambda s: "improve" if s["quality_score"] < 6 else "end",
        {"improve": "improve", "end": END})
    workflow.add_edge("improve", "evaluate")                # the loop
    return workflow.compile()

Parallel execution — why fan-out is actually concurrent

When a node has multiple outgoing edges to independent nodes, LangGraph schedules those branches to run together rather than one-by-one, because nothing in state makes one depend on another's output yet. This is the mechanism behind tab ③'s "100 seconds → ~20 seconds" claim — it isn't a metaphor, it's how the fan-out graph actually executes.

Building Multi-Agent Systems in LangGraph

Phase B · Building

Putting ④'s supervisor-worker pattern together with ⑥–⑦'s state/node/edge/conditional-edge mechanics.

A supervisor-worker system in LangGraph is a graph where one node (the supervisor) is reached repeatedly, and a conditional edge out of it decides which worker runs next — instead of a fixed sequence.

class State(TypedDict):
    task: str
    research_notes: str
    sql_result: str
    draft: str
    next_worker: str      # the supervisor writes its routing decision here

def supervisor(state: State):
    # In production this call asks an LLM "given what's done so far, who goes next?"
    done = [k for k in ("research_notes","sql_result","draft") if state.get(k)]
    if "research_notes" not in done: nxt = "research_worker"
    elif "sql_result" not in done:    nxt = "sql_worker"
    elif "draft" not in done:         nxt = "writing_worker"
    else:                             nxt = "end"
    return {"next_worker": nxt}

def route(state: State):
    return state["next_worker"]

workflow.add_node("supervisor", supervisor)
workflow.add_node("research_worker", research_worker)
workflow.add_node("sql_worker", sql_worker)
workflow.add_node("writing_worker", writing_worker)

workflow.add_edge(START, "supervisor")
for worker in ["research_worker", "sql_worker", "writing_worker"]:
    workflow.add_edge(worker, "supervisor")      # every worker reports back to the supervisor
workflow.add_conditional_edges("supervisor", route,
    {"research_worker":"research_worker", "sql_worker":"sql_worker",
     "writing_worker":"writing_worker", "end": END})
┌──────────────────────────┐ ↓ │ Supervisor ──routes to──→ Worker runs ↑ │ └──────────────────────────┘ (every worker hands control back to the supervisor, which decides the NEXT worker — or END)
Common mistake. Letting workers call each other directly "to save a hop." It's tempting and it quietly destroys the supervisor's ability to track progress, retry a failed worker, or stop the process — the entire point of the pattern is that workers only talk to shared state and the supervisor, never to each other.

Hierarchical extension

A hierarchical system is this same shape, recursively: a "Research Supervisor" subgraph (with its own internal supervisor + workers) gets compiled and plugged in as a single node under a "Main Supervisor." LangGraph graphs can be nested as nodes — this is the actual implementation of the hierarchy diagram from tab ④.

Production: Failure Modes, Infra, Scaling

Phase C · Production

What breaks in a multi-agent system that never broke in a single agent, and what to put in place before it does.

Failure modeWhat it looks likeMitigation
Runaway loopQuality score never clears the threshold; graph loops until timeout or cost spikeMax-iteration counter in state, hard-capped and checked in the conditional edgefailure
State key collisionA parallel branch's output silently overwritten by a sibling branchOne state key per branch, or an explicit reducer (Annotated[list, add]-style merge)failure
Silent partial failureOne worker's LLM call errors; the graph proceeds with an empty/stale field instead of stoppingValidate each node's output before returning it; route failures to an explicit error/retry node, not past themfailure
Supervisor driftSupervisor keeps re-routing to the same worker because its "done" check is wrongMake completion conditions explicit booleans in state, not inferred from free textfailure
Unbounded state growthLong-running graphs accumulate huge message histories, re-sent to every LLM callSummarize/trim history fields; don't let every node read the full raw historyfailure
No resumabilityA crash mid-graph loses all completed workLangGraph checkpointing (e.g. SqliteSaver/PostgresSaver) persists state after every nodeproduction

Infrastructure checklist

  • Checkpointing — persist state after each node so a crash resumes instead of restarting from scratch.
  • Tracing — every node call, its input/output, and latency logged (LangSmith or an equivalent) so a bad final answer can be traced back to the node that caused it.
  • Retries with backoff — per-node, not per-graph: retrying the whole graph because one worker's API call timed out re-does work that already succeeded.
  • Cost/latency budgets — a parallel fan-out of five LLM calls is five times the cost of one; know that multiplier before shipping.
  • Human-in-the-loop gates — for any action with real-world side effects (sending an email, making a purchase), an explicit pause node rather than trusting the supervisor's judgment alone.
Common mistake. Treating "it worked in the notebook" as "it's production-ready." A notebook run is one trajectory through the graph with no concurrent users, no transient API failures, and a human watching. Production is thousands of trajectories, some of which will hit every failure mode above simultaneously.
Analogy — a kitchen on a Saturday night, not a cooking class. In the class (the notebook), one dish, one cook, no pressure. On a Saturday night, a burned station needs to be caught and 86'd before it reaches the pass (tracing), the kitchen keeps running if one burner dies (resumability), and the head chef has a hard rule on how many times a dish gets sent back before it just goes out as-is (max-iteration guard).

Evaluation: Verifying It Actually Works

Phase C · Production

"It ran without an exception" and "it worked" are different claims. This tab is about proving the second one.

Three levels to evaluate

Per-node

Did this node's output meet its own bar? (e.g. did the SQL worker generate valid SQL?)

Trajectory

Did the graph take a reasonable path — right workers, right order, no wasted loops?

End-to-end

Did the final answer actually solve the user's task?

Trajectory evaluation

Log the sequence of node names the graph actually visited for a given input, then compare against an expected (or acceptable-set of) trajectories. A system that reaches the right final answer by routing through every worker twice is not healthy, even if the end-to-end score looks fine.

expected_trajectory = ["supervisor", "research_worker", "supervisor", "writing_worker", "supervisor"]
actual_trajectory   = [step["node"] for step in app.get_state_history(config)]
trajectory_match    = actual_trajectory == expected_trajectory   # exact, or use edit-distance for "close enough"

LLM-as-judge for subjective outputs

For free-text outputs (a marketing message, a research summary) a second LLM call scores the result against a rubric — exactly the pattern tab ⑦'s evaluate_quality node simulated with random.randint(). In production that random stub becomes:

def evaluate_quality(state: State):
    response = judge_llm.invoke(f"""Rate this product description from 1-10 for clarity,
persuasion, and relevance. Return only the number.\n\n{state['final_description']}""")
    return {"quality_score": int(response.content.strip())}
Common mistake. Using the same LLM call, same prompt, as both a worker and its own judge. It tends to rate its own output generously. Use a different prompt (ideally a different, cheaper model) dedicated only to scoring, and anchor it with a rubric and a few examples.

Tracking it over time

A single run's score tells you little; a test set of 15-20 representative tasks, re-run after every prompt or graph change, tells you whether a change actually helped. This is the same discipline regression tests bring to normal software — multi-agent systems need it more, not less, because small prompt edits can silently change routing behavior.

Code Lab: Progressive Build

Code · Runnable in Google Colab

Five programs, each adding exactly one concept, building toward a real supervisor-worker system. Programs 1-3 extend the product-description workflow; programs 4-5 build the multi-agent layer on top.

Program 1 — Sequential graph (state, node, edge)

The minimal graph: one state, four nodes in a straight line.

# pip install -U langgraph langchain langchain-openai
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, SystemMessage
import os, getpass

os.environ["OPENROUTER_API_KEY"] = getpass.getpass("OpenRouter API key: ")
llm = ChatOpenAI(model="openai/gpt-4o-mini", temperature=0.3,
                  openai_api_key=os.environ["OPENROUTER_API_KEY"],
                  base_url="https://openrouter.ai/api/v1")

class State(TypedDict):
    product_name: str; basic_description: str
    features_benefits: str; marketing_message: str; final_description: str

def generate_basic_description(state: State):
    r = llm.invoke([SystemMessage(content="You write brief product descriptions."),
                     HumanMessage(content=f"Describe '{state['product_name']}' in one sentence.")])
    return {"basic_description": r.content}

def add_features_benefits(state: State):
    r = llm.invoke(f"List key features and benefits of:\n{state['basic_description']}")
    return {"features_benefits": r.content}

def create_marketing_message(state: State):
    r = llm.invoke(f"Create a compelling marketing message using:\n{state['features_benefits']}")
    return {"marketing_message": r.content}

def polish_final_description(state: State):
    r = llm.invoke(f"Polish and finalize this description:\n{state['marketing_message']}")
    return {"final_description": r.content}

workflow = StateGraph(State)
for label, fn in [("basic", generate_basic_description), ("features", add_features_benefits),
                   ("marketing", create_marketing_message), ("final", polish_final_description)]:
    workflow.add_node(label, fn)
workflow.add_edge(START, "basic"); workflow.add_edge("basic", "features")
workflow.add_edge("features", "marketing"); workflow.add_edge("marketing", "final")
workflow.add_edge("final", END)
app = workflow.compile()

result = app.invoke({"product_name": "Smart Water Bottle", "basic_description": "",
                      "features_benefits": "", "marketing_message": "", "final_description": ""})
print(result["final_description"])
Program 2 — Parallel fan-out / fan-in

Adds: three independent branches off basic, merging into marketing. New concept only — the imports and llm setup from Program 1 are unchanged.

class State(TypedDict):
    product_name: str; basic_description: str; features_benefits: str
    target_audience: str; seo_keywords: str; marketing_message: str; final_description: str

def add_features(state): return {"features_benefits": llm.invoke(f"Features/benefits:\n{state['basic_description']}").content}
def identify_audience(state): return {"target_audience": llm.invoke(f"Target audience for:\n{state['basic_description']}").content}
def generate_seo_keywords(state): return {"seo_keywords": llm.invoke(f"SEO keywords for:\n{state['basic_description']}").content}

def create_marketing_message(state: State):
    combined = f"Features:\n{state['features_benefits']}\n\nAudience:\n{state['target_audience']}\n\nSEO:\n{state['seo_keywords']}"
    return {"marketing_message": llm.invoke(f"Compelling marketing message using:\n{combined}").content}

workflow.add_node("basic", generate_basic_description)

Program 4 — Supervisor-worker multi-agent system

Adds: the multi-agent layer from tab ⑧ — a supervisor node and a conditional edge that routes to whichever worker hasn't run yet.

class MASState(TypedDict):
    task: str; research_notes: str; draft: str; final_description: str; next_worker: str

def research_worker(state: MASState):
    return {"research_notes": llm.invoke(f"Research key facts for: {state['task']}").content}

def writing_worker(state: MASState):
    return {"draft": llm.invoke(f"Write a draft using:\n{state['research_notes']}").content}

def polish_worker(state: MASState):
    return {"final_description": llm.invoke(f"Polish:\n{state['draft']}").content}

def supervisor(state: MASState):
    if not state.get("research_notes"): nxt = "research_worker"
    elif not state.get("draft"):        nxt = "writing_worker"
    elif not state.get("final_description"): nxt = "polish_worker"
    else: nxt = "end"
    return {"next_worker": nxt}

workflow = StateGraph(MASState)
workflow.add_node("supervisor", supervisor)
for label, fn in [("research_worker", research_worker), ("writing_worker", writing_worker), ("polish_worker", polish_worker)]:
    workflow.add_node(label, fn)
    workflow.add_edge(label, "supervisor")     # every worker reports back

workflow.add_edge(START, "supervisor")
workflow.add_conditional_edges("supervisor", lambda s: s["next_worker"],
    {"research_worker": "research_worker", "writing_worker": "writing_worker",
     "polish_worker": "polish_worker", "end": END})
app = workflow.compile()
result = app.invoke({"task": "Smart Water Bottle launch copy", "research_notes": "", "draft": "", "final_description": "", "next_worker": ""})

Assignment 2 — Integration Challenge Intermediate

Tests: Tab ⑦ fan-out/fan-in, Tab ④ shared state, Tab ⑤ deciding when LangGraph is warranted.

Scenario. Extend Assignment 1's ticket triage into a parallel system: once categorize runs, fan out to three independent agents — a Priority Agent (urgent/normal/low), a Sentiment Agent (angry/neutral/positive), and a Similar-Tickets Agent (given a small hardcoded list of 10 past tickets, pick the most similar one) — then fan in to a Routing Agent that combines all three into a final routing decision (which team, what priority flag).

Requirements.

  • Must-have: three branches run as true fan-out (not three sequential calls disguised as "parallel"); each writes a distinct state key; a single fan-in node reads all three.
  • Nice-to-have: a conditional edge that skips the Similar-Tickets Agent entirely when the Priority Agent already says "urgent" (saves a call on the cases that matter least for it).
💡 Hint — structuring the fan-out
Give each branch its own key (priority, sentiment, similar_ticket) exactly like tab ⑦'s features/audience/seo split. Wire all three edges from categorize, and all three into route_ticket.
💡 Hint — the skip-on-urgent conditional edge
This needs add_conditional_edges out of the Priority Agent itself, not out of categorize — the routing function reads state["priority"] and returns either "similar_tickets" or straight to "route_ticket".

Evaluation criteria (not just "does it run"): Does disabling the skip-logic measurably slow it down (proving the branches really were parallel)? Does the final routing decision actually change when you feed it an angry, urgent ticket vs. a calm, low-priority one?

Self-Check

  • ☐ If two branches write to the same key by mistake, does one silently disappear? (Confirm you understand why, from tab ④.)
  • ☐ Does the Similar-Tickets Agent actually get skipped on an urgent ticket, provable by a print statement or trace?
  • ☐ Does the final decision differ for at least two meaningfully different test tickets?

Assignment 3 — Production Capstone Advanced

Tests: Tab ⑧ supervisor-worker, Tab ⑨ failure modes/guards, Tab ⑩ evaluation.

Scenario. Your team wants Assignment 2's triage system running against a live queue, not a one-off call. Convert it to a supervisor-worker architecture: a supervisor decides whether a ticket needs the full parallel analysis (Assignment 2's path) or can take a fast path (a single LLM call) when it's an obvious duplicate of something in the similar-tickets list — this is the one required advanced pattern (routing-based short-circuiting, the lightweight cousin of query routing).

Requirements spec.

  • A supervisor node that inspects the similar-tickets match confidence and routes to either the fast path or the full Assignment-2 graph (as a nested subgraph node, per tab ⑧'s hierarchical-extension note).
  • A max-iteration / max-retry guard on any loop you introduce (tab ⑨).
  • An evaluation harness: 10 test tickets with a hand-labeled expected category + priority, scored for exact-match accuracy, plus a trajectory check that fast-path tickets never visit all three parallel agents (tab ⑩).
🏗️ Architecture hint
Compile the Assignment-2 graph as its own object, then add it as a single node (workflow.add_node("full_analysis", assignment2_app)) inside the new top-level graph — LangGraph treats a compiled graph as a callable, so this "just works" as a node.
