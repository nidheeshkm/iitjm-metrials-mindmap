The five ideas everything else stands on

Phase A, foundations: what and why

If any idea on this page feels fuzzy, every later tab will feel like magic, and magic is impossible to debug at 3 a.m. Spend fifteen minutes here.

1. What an LLM knows, and what it doesn't

A large language model (LLM) is a next-word predictor trained on a huge snapshot of public text. It knows general engineering well. It has never seen your runbooks, your incident history, or last Tuesday's deploy.

🧭 Analogy: the brilliant new hire.On day one they know HTTP status codes and caching theory cold, but have never opened your team wiki. Ask "how do we purge the CDN for brand B?" and you get a confident, generic, possibly wrong answer.

Example. Ask a bare LLM "What does AUTH-403 mean on our storefront?" It will guess "forbidden, check permissions", because AUTH-403 is your internal code and it has no way to know your code means "the client secret was rotated but not updated".

⚠️ Common mistake:fine-tuning a model "so it learns our runbooks". Likely Fine-tuning shifts style and behaviour far more reliably than it stores facts, and facts that change weekly would force retraining weekly. Facts belong in retrieval; behaviour belongs in prompts or fine-tuning.

2. Tokens and the context window

Models read tokens, chunks of text roughly three-quarters of an English word long. The context window is how many tokens fit in one request: your instructions, the retrieved text, and the answer, all together.

🧭 Analogy: the exam-room whiteboard.Big, but finite. You can't tape the whole library to it, so you choose which pages to copy up. Retrieval is the act of choosing.

Example. Likely A 300-page PDF is on the order of 150,000 tokens. Even if a model accepts that much, you pay for every token on every question, and answers get worse for facts buried in the middle (Tab ⑩ covers "lost in the middle").

⚠️ Common mistake:"long-context models make RAG obsolete." They reduce chunking pain, but cost and latency still scale with tokens, and you still need to know which 5 pages matter out of 50,000.

3. Vectors and similarity

A vector is just a list of numbers. An embedding model turns a piece of text into one, trained so that texts with similar meaning land close together.

🧭 Analogy: GPS coordinates for meaning."Checkout is slow" and "payment page latency is high" get nearby coordinates even though they share no words, the way two cafés on the same street have nearby coordinates even with different names.

Worked example (2 dimensions instead of 384).

TextToy vectorCosine vs "checkout slow"
checkout slow(0.90, 0.10)1.000
payment latency high(0.80, 0.30)0.969 (very close)
CDN cache purge(0.10, 0.95)0.214 (far)

Cosine similarity measures the angle between two arrows: cos(A,B) = (A·B) / (|A| × |B|). 1 means same direction, 0 means unrelated. If vectors are normalized to length 1, cosine equals the plain dot product, which is why every code example in this guide normalizes.

⚠️ Common mistake:treating a similarity score as a probability, or reusing one threshold across models. Certain Score scales differ per model: 0.62 can be a strong match in one model and noise in another. Thresholds must be calibrated per model on your data (Tab ⑪).

4. RAG in one picture

Retrieval-Augmented Generation (RAG) = find the relevant pages first, then let the LLM answer using only those pages.

Offline: indexing (once, then on every doc change) Documents→Split into chunks→Embed each chunk→Store vectors + metadata
Online: answering (every question) Question→Embed question→Search vector DB→Top-k chunks→Prompt = question + chunks→LLM→Answer with citations

🧭 Analogy: the open-book exam.The student (LLM) is smart; the textbook (your docs) holds the facts; the index at the back (vector DB) finds the right pages fast.

Embeddings, embedding models, and chunking

Phase A, foundations: what and why

Everything downstream, including Qdrant, the reranker and every grader, can only work with what the embedding step lets through. A bad embedding choice can't be fixed by a clever loop later.

What an embedding model actually does

An embedding model is a neural network that reads a text and outputs a fixed-length vector, say 384 numbers, no matter whether the text is three words or three paragraphs. Training pushed texts with similar meaning toward similar vectors.

🧭 Analogy: shelving a library by meaning.A normal library shelves alphabetically, so "Cooking for Beginners" and "Kitchen Basics" end up far apart. An embedding library shelves by what the book is about, so they sit side by side, and your question walks straight to that shelf.

Example. With bge-small-en-v1.5, "checkout is very slow" and "payment page latency is high" score around 0.7–0.8 cosine, while "check out this new book" scores noticeably lower despite sharing the word "check out". Likely Exact numbers vary; Program P1 in Tab ⑫ prints them for you.

Bi-encoders: why search can be fast

The models in this tab are bi-encoders: they embed the query and each document separately. That means documents can be embedded once, ahead of time, and a query costs one embedding plus a nearest-neighbour lookup.

🧭 Analogy: school ID photos.Every student's photo is taken once at enrolment (documents embedded offline). At the gate, the guard only photographs the visitor and compares (query embedded online). Nobody retakes the whole school's photos per visitor.

The price: the model never sees query and document together, so it can miss subtle relevance. Tab ⑥ fixes that with a cross-encoder reranker on a short list.

Chunking: cutting documents into retrievable pieces

You don't embed a whole 40-page runbook as one vector: its meaning would be an average of everything, which matches nothing well. You split it into chunks.

🧭 Analogy: index cards vs the whole textbook.If you revise with one summary card per book, you can't find the formula you need. One card per paragraph and you lose which chapter it came from. Good chunking is sized so each card answers one kind of question and carries a note of where it came from.

StrategyHow it splitsGood forWatch out for
Fixed sizeEvery N characters or tokensQuick baselinesCuts mid-sentence, mid-table
Recursive characterTries paragraph, then line, then sentence, then word boundaries until chunks fitDefault for prose and PDFsStill blind to document structure
Structure-awareSplits on headings, list items, HTML/Markdown sectionsRunbooks, wikis, API docsNeeds clean source formatting

A sane starting point. Likely 600–1,000 characters (roughly 150–250 tokens) with 10–15% overlap, recursive splitting. Tune with your golden set (Tab ⑪), not by feel.

Chunks too small

"Increase the pool only if saturation exceeds 80%" gets separated from "Payment authorization timeouts:". The chunk matches, but the LLM doesn't know what pool.

Chunks too large

A chunk covering payments, CDN and deploys has a vector that's a blurry average; it ranks medium for everything and first for nothing.

Metadata is decided at chunk time

Every chunk should carry: source file, page or section, and the business fields you'll filter on later (service, doc type, severity, date). Tab ⑤'s filters can only use what you stored here.

⚠️ Common mistake:chunking without metadata "to add later". Adding a field later means re-reading every source and re-upserting every point. Decide your filter fields before the first ingestion.

🎓 AIOps link.For incident runbooks, structure-aware chunking on headings ("Symptoms", "Diagnosis", "Mitigation") usually beats fixed size, because on-call questions map onto those sections. Store the section name in the payload so the generator can say "from the Mitigation section of the checkout runbook".

Qdrant: the vector database

Phase B, building: architecture and trade-offs

Qdrant stores your vectors with their metadata, finds nearest neighbours in milliseconds, and filters by metadata during the search rather than after. That last property is why this guide uses it.

🧭 Analogy: a library with a smart card catalogue.The vector is the shelf location (where the book sits by meaning). The payload is everything written on the catalogue card: author, year, section. A good librarian uses both at once: "books near this topic, but only from the 2025 shelf."

How search stays fast: HNSW

Comparing a query to a million vectors one by one is too slow. Qdrant builds an HNSW (Hierarchical Navigable Small World) graph: each vector links to a few near neighbours, with sparse "express" layers on top.

🧭 Analogy: motorway then local roads.To reach a house in another city you take the motorway to the right region, then main roads, then side streets. HNSW's top layers are motorways; the bottom layer is the street where each vector lives.

Likely Defaults are m=16, ef_construct=100; they're fine until your evaluation shows recall loss. HNSW is approximate: it can occasionally miss a true nearest neighbour. For small collections Qdrant may just scan exactly.

Distance metrics

Choose Distance.COSINE for sentence-transformer models. Qdrant normalizes vectors on insert for cosine, so you don't have to. DOT only if your model expects unnormalized dot product; EUCLID rarely for text.

A question about checkout has no business matching CDN postmortems. Filters shrink the search space before similarity ranking, which improves both precision and speed, if you set them up right.

🧭 Analogy: asking the librarian properly."Something about slow pages" gets you a cart of books. "Something about slow pages, only the e-commerce section, published after 2024, not the case-study shelf" gets you three books, all useful.

Payload indexes and the query planner

Qdrant decides per query how to combine filter and vector search. If a filter is very selective (say 40 matching points), it can just score those 40 exactly. If it's broad, it walks the HNSW graph while checking the filter. Likely It estimates selectivity using payload indexes, and on the server it adds extra graph links for indexed fields so filtered walks don't get stranded.

  • Create a payload index for every field you filter on: keyword for categories, integer for years, datetime for timestamps.
  • Likely Create indexes before bulk upload, so the HNSW graph is built with them in mind.
  • Don't index fields you never filter on; each index costs memory.

⚠️ Common mistake:filtering on an unindexed field in production. It works in the demo with 12 points and crawls at 2 million. Some Qdrant configurations (strict mode) can reject unindexed filters outright. Likely

Filters inside Self-RAG: the self-query step

In Tab ⑨ the router LLM extracts filters from the question: "checkout 429s since the last release" becomes service=checkout. Two rules make this safe:

  1. Validate against an allow-list. If the LLM says service="checkout-api" and your payload only has "checkout", you get zero results and the loop starts rewriting forever. Map or drop unknown values.
  2. Relax on retry. If a filtered attempt yields nothing relevant, retry without the least important condition before rewriting the query. Over-filtering is one of the most common reasons Self-RAG "can't find" answers that exist.

Hybrid search and Cohere Rerank

Phase B, building: architecture and trade-offs

Dense search understands meaning but fumbles exact tokens. Keyword search nails exact tokens but misses paraphrases. Run both, fuse, then let a slower, smarter model reorder the short list.

🧭 Analogy: two ways to fish.The net (dense search) sweeps everything in the right area, including fish you didn't name. The spear (BM25) hits exactly the fish you point at, "AUTH-403", and nothing else. Experienced fishers carry both.

Sparse vectors and BM25 in Qdrant

BM25 represents text as a sparse vector: one dimension per vocabulary word, almost all zeros. Qdrant stores these next to dense vectors in the same point (named vectors) and applies IDF weighting server-side when you set modifier=IDF. The fastembed library's Qdrant/bm25 model produces the sparse vectors locally.

Fusing two ranked lists: Reciprocal Rank Fusion

Dense and BM25 scores are on different scales, so you can't add them. RRF ignores scores and uses ranks:

RRF(doc) = Σ over lists of 1 / (k + rank), with k = 60

DocDense rankBM25 rankRRF score
AUTH-403 runbook411/64 + 1/61 = 0.0320
General login doc1—1/61 = 0.0164
SLAS config doc251/62 + 1/65 = 0.0315

Documents that appear in both lists win, which is exactly the behaviour you want. Qdrant runs RRF server-side via prefetch + FusionQuery.

The rerank score as a quality gate

If the best reranked document scores very low, retrieval probably failed. That signal feeds Self-RAG (Tab ⑨: skip or trigger grading) and CRAG (Tab ⑦: web fallback). Phase B, building: architecture and trade-offs

Self-RAG architecture: from reflection tokens to a state graph

Phase B, building: architecture and trade-offs

First the original idea, because it explains why each grader exists. Then the architecture you'll actually build: the same four judgments, implemented as nodes in a LangGraph loop.

The paper in one page

Certain Self-RAG was introduced by Asai et al. in "Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection" (arXiv 2310.11511, 2023; ICLR 2024). The model generates special reflection tokens alongside normal text:

TokenQuestion it answersPossible values
RetrieveDo I need to look something up for the next segment?yes / no / continue (reuse evidence)
IsRelIs this retrieved passage relevant to the question?relevant / irrelevant
IsSupIs what I just wrote supported by the passage?fully / partially / no support
IsUseIs the overall response useful for the question?5 (best) to 1

Likely How it was trained: a critic model learned to produce these judgments from GPT-4-labelled examples; the critic then annotated a large corpus, and a generator (Llama 2 7B and 13B) was trained to emit the tokens itself. At inference it can retrieve on demand per segment, draft continuations for several passages in parallel, and pick the best with a score mixing fluency and critique-token probabilities; weights on those critiques can be changed at inference time to trade fluency for strict support.

🧭 Analogy: the careful doctor.Decides whether to order tests (Retrieve), reads each lab report for relevance (IsRel), checks the diagnosis is backed by results (IsSup), and asks whether the explanation actually helps the patient (IsUse).

Why a graph and not a chain

  • Loops. Chains flow one way; Self-RAG must go back to retrieval. LangGraph's conditional edges express this directly.

The pipeline, step by step: multi-query, dedup, grading, rewriting

Phase B, building: patterns and trade-offs

Each step below has one job, one input, one output, and one typical way of failing. Build and test them one at a time (Programs P7–P9) before wiring the loop.

🧭 Analogy: a kitchen line.Prep cook widens the order (multi-query), the pantry pulls ingredients (retrieve), someone throws out duplicates and spoiled items (dedup, grade), the chef cooks (generate), and the pass checks every plate against the ticket before it leaves (grounded, useful). A plate that fails goes back, but only twice before the manager steps in (fallback).

Full order of operations 1. Route→2. Transform query→3. Retrieve (hybrid, filtered)→4. Dedup→5. Rerank→6. Grade docs→7. Generate→8. Grounded?→9. Useful?→Answer Gates (purple) can send the flow back to 10. Rewrite, or out to 11. Fallback.

1. Route: retrieve or not, and with what filters

Input: the question. Output: needs_retrieval and optional filter fields. "What's 17 × 3?" → no. "How do I purge the eCDN for one brand?" → yes, service="cdn".

Use structured output with an explicit list of allowed filter values in the prompt, then validate in code (Tab ⑤). Default to retrieving when unsure; a wasted retrieval costs milliseconds, a skipped one can cost a wrong answer.

2. Transform the query

Multi-query example. "checkout keeps failing with too many requests" becomes: (a) original, (b) "checkout API HTTP 429 rate limit", (c) "SCAPI quota exceeded checkout errors", (d) "throttling on basket and order endpoints". Query (b) is the one that hits the runbook's wording.

⚠️ Common mistake:letting multi-query run with no cap. 5 queries × 30 results = 150 candidates to dedup and rerank on every question. Cap at 3 extra queries and 10–20 results each.

3. Retrieve

Per query: hybrid search (Tab ⑥) with the validated filter (Tab ⑤). On a retry after a failed attempt, drop the filter first; rewrite second.

4. Dedup: four layers, cheapest first

Example. 4 queries × 10 results = 40 hits → 17 unique IDs → 15 unique texts → 13 after near-dup removal → reranker sees 13, not 40. That's a 3× cut in rerank cost for zero quality loss.

⚠️ Common mistake:running near-duplicate removal with too low a threshold (say 0.85). Two genuinely different runbook steps about the same service get merged and the answer loses a step. Check what you drop.

5. Rerank

Cohere (or local cross-encoder) on the deduplicated pool; keep top 5–8. This is the cheapest precision boost in the whole pipeline, so it runs before the expensive LLM graders, never after.

6. Grade documents (IsRel)

For each surviving chunk: does it help answer this question? Design choices that matter:

  • Batch it. One call grading 6 documents returning a list of relevant indexes, instead of 6 calls. Same quality in practice for short chunks, 5 fewer round-trips. Likely
  • Reason before verdict. Put a short reasoning field before the verdict field in the schema. The model writes its justification first, then decides, which tends to improve consistency.
  • Define relevance for your domain. "Mentions checkout" is not relevant to "how to fix checkout 429s"; "explains the rate-limit fix" is. Spell this out.
  • Temperature 0, small fast model. Graders are classifiers, not writers.

Grader too strict

Rejects everything, context is empty, loop rewrites until fallback. Symptom: high fallback rate on questions you know are answerable.

Grader too lenient

Keeps everything; you've added a second of latency for nothing. Symptom: grader keep-rate near 100% in logs.

7. Generate

Only relevant docs go in, numbered [1]..[n]. The prompt demands citations and explicitly permits "the sources don't cover this". Put the strongest document first and second-strongest last; weak evidence in the middle is where models pay least attention.

8. Check grounded (IsSup)

Input: the docs and the answer. Output: unsupported_claims (list) then grounded (bool). Asking for the list first forces the grader to actually look. If not grounded and a regeneration is left, regenerate with a stricter instruction; otherwise fall back.

Example. Answer says "increase the connection pool to 200". Source says "increase the pool only if saturation exceeds 80%". Unsupported claim: the number 200. Verdict: not grounded.

9. Check useful (IsUse)

Grounded is not the same as helpful. "The checkout runbook discusses 429 errors [1]" is perfectly grounded and useless. Input: the original question and the answer. Output: useful. If not useful, the problem is usually the evidence, so rewrite the query rather than regenerate.

10. Rewrite

Give the rewriter the original question, the last search query, and why it failed ("retrieved docs were about CDN purges"). Blind rewriting tends to produce near-synonyms of the query that just failed.

11. Fallback

When budgets run out, say so plainly and show what was found: "I couldn't find a runbook that answers this. Closest sources: [checkout runbook, section Mitigation]." For on-call use, a clear "not found" with pointers is a correct outcome, and your evaluation must count it as one for unanswerable questions (Tab ⑪).

LLM-as-judge pitfalls

  • Self-preference: a model grading its own family's answers tends to be generous. Use a different model family as judge.
  • Verbosity bias: longer answers get higher scores. Include a short correct answer in your spot checks.
  • Drift: judge scores are only comparable within one judge model and prompt. Changing the judge resets your baseline.
  • Trust, but spot-check: read 10% of judgments yourself each run.

✅ Make it a regression gate.Run the harness whenever you change a prompt, model, chunk size or embedding model. Fail the change if Hit@5 or faithfulness drops beyond a tolerance you set. This is the same idea as a CI test suite, applied to answer quality.

Architecture hint: parallel verification

Running grounded and useful checks together saves one round-trip on the happy path but wastes a useful-check call when the answer isn't grounded. Measure how often generation fails grounding; if it's rare, parallel wins. A single verify node returning both verdicts keeps the graph simple.

Architecture hint: calibrating the confidence gate

Run the golden set with the gate disabled and log (top rerank score, did the grader keep the top doc?). Choose the lowest threshold above which the grader kept the top doc in every case. Re-check after any reranker change: Cohere and local cross-encoder scores live on different scales.

Architecture hint: filter relaxation order

Drop the most specific condition first (usually min_year, then doc_type, then service). Log each relaxation in the trace so you can see how many answers depended on it.

Architecture hint: the alias drill

Qdrant's update_collection_aliases can delete the old alias link and create the new one in a single atomic request. Your app should reference only copilot_live; if any code mentions copilot_v2 directly, the drill fails.
