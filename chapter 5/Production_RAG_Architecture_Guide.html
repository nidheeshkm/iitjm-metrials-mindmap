The 30-second mental model: A RAG system is an open-book exam taker. The LLM is a smart student who is excellent at writing coherent answers but has no idea what's actually in your company's handbook. Before the student answers, you hand them the 2–3 most relevant pages from the handbook. "Production RAG" is everything you build so that (a) you hand them the right pages, (b) you catch it when you can't find the right pages, and (c) you stop students from being tricked into revealing the staff room combination lock code.
Why "production" changes everything
A RAG demo is: embed some text, search it, stuff it in a prompt. A RAG demo breaks in production because of things a demo never encounters: a question with no good answer in the docs (the system should say so, not hallucinate); a question phrased with the wrong words for semantic search to catch (needs keyword search too); a question that needs live data no document contains (needs tool-calling); a user trying to extract secrets (needs guardrails); and a stakeholder asking "how do we know it's actually working?" (needs evaluation). This guide is built around closing each of those five gaps, in order.

Phase A — Foundations

③ Embeddings, chunking, and dense retrieval with Qdrant

What an embedding actually is

Library analogy: Imagine every book in a library is placed on a shelf not alphabetically, but by meaning — cookbooks cluster together, and within that cluster, Italian cookbooks sit closer to each other than to baking books. An embedding model does this for text: it reads a sentence and outputs a list of numbers (a vector) that is its "shelf position" in meaning-space. Two sentences about the same topic get vectors that sit close together, even if they don't share a single word.

Concretely: all-MiniLM-L6-v2 (the model used throughout this guide) turns any sentence into a 384-number vector. "Employees get 24 days of leave" and "How much annual leave do staff receive?" land close together in that 384-dimensional space, even though they share almost no words.

# every embedding model: text in, fixed-length vector out
embedding_model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
vector = embedding_model.encode("Employees get 24 days of leave", normalize_embeddings=True)
# vector.shape == (384,) — same length no matter how long the input sentence is

[Certain] Why normalize? With normalized (unit-length) vectors, cosine similarity reduces to a simple dot product, which is what lets a vector database compare millions of vectors fast. normalize_embeddings=True is why the rest of this guide can use plain cosine distance in Qdrant.

⚠️ Common mistake
Assuming embeddings understand exact strings the way a database index does. Embeddings are built for meaning, which means they are often weak on exact identifiers — an error code like VPN-403 or a SKU like SKU-2847 can embed close to lots of unrelated text, because the model has never seen that token behave like a meaningful unit. This exact gap is why Tab ④ adds keyword search back in.

Chunking: deciding what one vector represents

Kitchen analogy: You wouldn't blend an entire cookbook into one smoothie and expect to taste "chapter 4." You chop it into recipes, and each recipe is one retrievable unit. Chunking is the same decision for documents: what's the smallest independently-meaningful unit you're willing to retrieve and hand to the LLM?

The reference notebook uses the simplest possible chunking strategy: one chunk per policy document (12 short HR/IT policies, each a self-contained paragraph). That works because each document already is one coherent idea. In Tab ⑨ we'll cover what breaks when real documents are pages long.

⚠️ Common mistake
Forgetting that a cosine-similarity collection and a dot-product collection behave identically only when every vector is normalized. Mixing a non-normalized query vector against normalized stored vectors silently returns wrong rankings — nothing errors, the scores just stop meaning what you think they mean.

Failure mode: when dense retrieval alone isn't enough

failure Dense retrieval returns the semantically closest chunks — not necessarily the chunks that actually answer the question. On a small, clean 12-document set like this lab's, that rarely matters. At enterprise scale with thousands of overlapping documents, "semantically close" and "actually relevant" diverge often enough that Tab ④'s hybrid search becomes necessary, not optional.

Phase B — Building

④ Lexical search (BM25) and hybrid retrieval with RRF

Why add keyword search back in

As covered in Tab ③, dense embeddings are weak on exact tokens. BM25 is the opposite: it's a decades-old statistical scoring function that rewards documents containing the exact words of the query, weighted by how rare and how concentrated those words are. It has no idea what a word "means" — it only counts.

def tokenize(text):
    return re.findall(r"[a-z0-9]+", text.lower())

bm25_corpus = [tokenize(doc["title"] + " " + doc["text"]) for doc in documents]
bm25 = BM25Okapi(bm25_corpus)   # rank_bm25 library

def bm25_retrieve(query, top_k=5):
    scores = bm25.get_scores(tokenize(query))
    top_idx = np.argsort(scores)[::-1][:top_k]
    return [{"id": documents[i]["id"], "title": documents[i]["title"],
              "text": documents[i]["text"], "bm25_score": float(scores[i])} for i in top_idx]

Combining two rankings: Reciprocal Rank Fusion

You now have two ranked lists — dense and BM25 — scored on completely different, incomparable scales (cosine similarity vs. a BM25 statistic). RRF solves this by throwing away the raw scores and using only rank position: a document gets 1 / (k + rank) points from each list it appears in, and points from both lists are summed.

def reciprocal_rank_fusion(dense_results, bm25_results, rrf_k=60, top_k=8):
    scores = {}
    for rank, item in enumerate(dense_results, start=1):
        scores[item["id"]] = scores.get(item["id"], 0) + 1 / (rrf_k + rank)
    for rank, item in enumerate(bm25_results, start=1):
        scores[item["id"]] = scores.get(item["id"], 0) + 1 / (rrf_k + rank)
    ranked_ids = sorted(scores, key=scores.get, reverse=True)[:top_k]
    return [doc_by_id[doc_id] for doc_id in ranked_ids]   # simplified

def hybrid_retrieve(query, candidate_k=6, final_k=8):
    dense = dense_retrieve(query, top_k=candidate_k)
    lexical = bm25_retrieve(query, top_k=candidate_k)
    return reciprocal_rank_fusion(dense, lexical, top_k=final_k)
Query→Dense top-6+BM25 top-6→RRF fuse by rank→top-8 fused candidates
Why rank, not score, is the right thing to fuse
decision A cosine score of 0.81 and a BM25 score of 9.3 cannot be averaged meaningfully — they live on unrelated scales that change with corpus size and embedding model. Rank position ("this was the #2 result") is comparable across any two retrieval methods, which is the entire reason RRF uses it instead of normalizing and averaging raw scores.
⚠️ Common mistake
Treating rrf_k (here, 60 — a widely-used default from the original RRF paper) as a cosmetic constant. A small rrf_k makes rank-1 dominate overwhelmingly; a large one flattens the fusion toward a near-even blend. Teams copy the default of 60 without ever checking whether it suits their corpus size and query style — it's a real tuning knob, not boilerplate.

Phase B — Building

⑤ Reranking, grounded generation, and conversation memory

Reranking: a second, more expensive opinion

Hybrid retrieval (Tab ④) is deliberately cheap and approximate — it has to scan the whole corpus fast. A reranker is the opposite: it's a model built specifically to score query/document pairs precisely, and it's too slow to run against every document, so it only ever looks at the shortlist hybrid search already narrowed down.

co = cohere.ClientV2(api_key=os.environ["COHERE_API_KEY"])

def cohere_rerank(query, candidates, top_n=3):
    response = co.rerank(model="rerank-v3.5", query=query,
                          documents=[c["text"] for c in candidates], top_n=top_n)
    return [{**candidates[r.index], "rerank_score": float(r.relevance_score)} for r in response.results]
8 fused candidates→Cohere Rerank→best 3, each with relevance_score 0–1
Retrieve cheap, rerank precise — the two-stage pattern
technique This cheap-then-precise shape (narrow with fast hybrid search, then score the shortlist with an expensive model) is the same pattern behind almost every production search system, not just RAG. Running the reranker over the full corpus instead of a shortlist would work but would be far too slow and expensive at any real scale.

Grounded generation: making the LLM stay on the page

The reranked contexts, the conversation memory, and the question all get assembled into one explicit prompt that instructs the model to answer only from what's given:

def generate_rag_answer(question, contexts):
    context_text = "\n\n".join(f"Context {i+1}: {c}" for i, c in enumerate(contexts))
    prompt = f"""Conversation memory:\n{memory_text()}\n\nQuestion:\n{question}\n\n
Retrieved context:\n{context_text}\n\nInstructions:
- Answer using only the retrieved context.
- If the answer is not supported, say that the internal documents do not provide enough information.
- Keep the answer concise."""
    return call_llm("You are a grounded enterprise RAG assistant.", prompt, temperature=0)

[Certain] Three details here matter more than they look: temperature=0 (deterministic, not creative, answers), an explicit instruction to say "not enough information" rather than guess, and a system prompt that frames the model's role before the data arrives.

Conversation memory: a sliding window, not a transcript

School analogy: A teaching assistant doesn't memorize every word of every office-hours conversation all semester — they remember roughly the last few exchanges well enough to follow up ("as you asked earlier..."). The notebook's memory does exactly this, capped at 4 turns.
conversation_memory = []
MAX_MEMORY_TURNS = 4

def add_to_memory(question, answer):
    conversation_memory.append({"question": question, "answer": answer})
    if len(conversation_memory) > MAX_MEMORY_TURNS:
        conversation_memory.pop(0)
⚠️ Common mistake
Letting memory grow unbounded "to be safe." Every turn kept in memory gets re-sent as prompt tokens on every subsequent call — unbounded memory is a silent, compounding cost and latency leak, and eventually blows the context window on long sessions.

Phase B — Building

⑥ Guardrails and tool routing — the smallest possible agent

Guardrails: rejecting before you even retrieve

Doctor analogy: A doctor's receptionist doesn't need medical training to recognize "can I have your colleague's prescription records" as a request to refuse before it ever reaches the doctor. A guardrail is that receptionist — a cheap check that runs before retrieval and generation, so a disallowed request never even gets expensive processing.
BLOCKED_PATTERNS = [r"reveal.*password", r"show.*api key", r"give.*credential",
                     r"bypass.*security", r"disable.*mfa"]

def guardrail_check(question):
    q = question.lower()
    for pattern in BLOCKED_PATTERNS:
        if re.search(pattern, q):
            return False, "I cannot help reveal credentials or bypass security controls."
    return True, "allowed"
⚠️ Common mistake
Mistaking a regex blocklist (what this lab uses, for teaching clarity) for a production guardrail. production Real guardrails combine policy rules, a trained classifier or moderation model, authentication, and access control — a regex list is trivially bypassed by rephrasing ("what's the password, spelled with spaces between each letter?"). Tab ⑨ returns to this gap.

Tool routing: when the answer isn't in any document

Some questions are legitimately outside the knowledge base — not because retrieval failed, but because the answer is live external data no internal document would ever contain ("what's the capital of Vietnam?"). The notebook routes these to an external API instead of searching internal documents at all.

COUNTRY_TERMS = ["capital of", "currency of", "population of", "country facts", "languages of"]

def should_use_country_tool(question):
    return any(term in question.lower() for term in COUNTRY_TERMS)

def country_tool(question):
    country = extract_country(question)
    item = requests.get(f"https://restcountries.com/v3.1/name/{country}", timeout=20).json()[0]
    context = f"Country: {item['name']['common']}\nCapital: {', '.join(item.get('capital', []))}\n..."
    answer = call_llm("Answer using only the supplied country facts.", f"Question: {question}\n\n{context}")
    return {"answer": answer, "contexts": [context], "route": "TOOL", "tool_used": "REST Countries"}
Question→Guardrail check→Tool Router──→External Tool (if matched)
This is agentic RAG's smallest unit
concept "Agentic" sounds like it requires a complex planning framework, but at its core an agent is just: a decision point that picks between multiple possible actions based on the input, rather than always doing the same thing. should_use_country_tool is a one-line agent. Tab ⑦ and ⑧ add more sophisticated decision points on top of this same idea.
⚠️ Common mistake
Keyword-matching intent detection ("capital of" in question) is fast and transparent but brittle — "tell me Vietnam's capital city" slips past it. failure Production systems typically route with a small classifier or the main LLM itself (function-calling / tool-use), trading a little latency for far better recall on intent.

Phase B — Building

⑦ Self-RAG — critique and retry

Self-RAG asks one question after generation: "Is my answer good enough?" If not, it rewrites the query and tries once more, using everything from Tabs ④–⑥ again on the second pass.

def critique_answer(question, answer, contexts):
    prompt = f"""Question: {question}\nAnswer: {answer}\nRetrieved context:\n{"".join(contexts)}
Return exactly one label:
PASS = the answer is directly supported by the context and answers the question.
RETRY = the answer is weak, unsupported, or the context is insufficient."""
    result = call_llm("You are a strict RAG quality checker. Return only PASS or RETRY.", prompt, temperature=0)
    return "PASS" if "PASS" in result.upper() else "RETRY"

def rewrite_query(question):
    return call_llm("Rewrite the query for enterprise document retrieval. Return only the rewritten query.",
                     f"Original query: {question}", temperature=0)

def self_rag(question):
    working_query = question
    for attempt in range(2):                       # capped at one retry
        candidates = hybrid_retrieve(working_query)
        reranked = cohere_rerank(working_query, candidates, top_n=3)
        contexts = [item["text"] for item in reranked]
        answer = generate_rag_answer(question, contexts)
        critique = critique_answer(question, answer, contexts)
        if critique == "PASS":
            return {"answer": answer, "contexts": contexts, "self_rag_attempts": attempt + 1}
        working_query = rewrite_query(question)
    return {"answer": answer, "contexts": contexts, "self_rag_attempts": 2}   # exhausted retries
Hybrid Retrieve→Rerank→Generate→Critique
PASS → return RETRY → rewrite query → retrieve again → rerank again → generate again → critique again → return regardless
⚠️ Common mistake
Assuming Self-RAG always improves the answer. Notice the final return statement: after the retry budget (here, 1 retry) is exhausted, the function returns whatever it has — even if the second critique also said RETRY. Self-RAG with a hard retry cap doesn't guarantee a good answer; it bounds the cost of trying, and silently gives up after that bound. A real system needs to surface low-confidence answers differently from high-confidence ones — which is exactly what CRAG (Tab ⑧) adds.
Cost and latency are not free here
failure Every RETRY branch doubles the LLM calls for that query: one more hybrid retrieve, one more rerank, one more generation, one more critique. At scale, a system where even 10% of queries RETRY once has its p99 latency and LLM spend dominated by that 10%. This is the trade-off row in Tab ②'s taxonomy table made concrete.

Phase C — Production

⑧ CRAG — correcting for weak retrieval, not just weak answers

Where Self-RAG (Tab ⑦) asks "is my answer good enough?", CRAG asks a different question before trusting anything: "Is my retrieved evidence reliable enough — and if not, what's my fallback?" It uses the top rerank score as a confidence signal.

CRAG_THRESHOLD = 0.20   # minimum acceptable rerank confidence — see Common Mistake below

def apply_crag(question, rag_result):
    retrieval = rag_result.get("retrieval", [])
    best_score = retrieval[0].get("rerank_score", 0.0) if retrieval else 0.0

    if best_score >= CRAG_THRESHOLD:
        return {**rag_result, "crag_action": "KEEP_RAG", "retrieval_confidence": best_score}

    if should_use_country_tool(question):
        tool_result = country_tool(question)
        return {**tool_result, "crag_action": "USE_TOOL", "retrieval_confidence": best_score}

    return {"answer": "I could not find reliable support for this question in the internal documents.",
            "contexts": rag_result.get("contexts", []), "crag_action": "SAFE_FALLBACK",
            "retrieval_confidence": best_score}
Self-RAG result→top rerank_score→≥ threshold?
Yes → KEEP_RAG (trust the evidence) No + tool matches → USE_TOOL No + no tool → SAFE_FALLBACK ("I don't know")
Fishing analogy: Self-RAG is a fisher who, after reeling in, checks "is this fish actually big enough to serve?" CRAG is the fisher checking, before even reeling all the way in, whether the line felt like it caught something real or just snagged on a rock — and if it was just a rock, switching to a different fishing spot (the tool) or admitting "nothing here" (safe fallback) instead of serving the rock as dinner.
⚠️ Common mistake
Treating CRAG_THRESHOLD = 0.20 as a production-ready constant because it appears in a working notebook. [Likely] This is a pedagogical placeholder, not a tuned value — the right threshold depends entirely on your reranker, your corpus, and how costly a wrong answer is for your use case. Shipping this number unchanged is the single most common way teams carry a toy project's assumptions into production.
CRAG's real contribution: graceful degradation
concept The property that matters isn't the specific threshold — it's that the system has three distinct outcomes (trust it / redirect it / admit failure) instead of two (answer / don't answer). A system that can only say "here's an answer" or "I refuse" either over-answers on weak evidence or under-answers on borderline-fine evidence. A third, explicit "I don't know, and here's why" path is what makes a system trustworthy enough to deploy against real users.

Scaling the vector database

This guide's Qdrant runs :memory: — fine for 12 documents, gone the moment the process restarts. production

  • Persistence: a real deployment points at Qdrant Cloud or a self-hosted Qdrant server with a disk-backed storage path, not :memory:.
  • Sharding/replication: collections split across nodes once document counts reach the millions, and replicated for availability.
  • Payload indexing: at scale, filter fields (department, access level, document date) need their own Qdrant payload indexes or every filtered query degenerates into a full scan.

Security and access control

Nothing in this guide's code checks who is asking. A production RAG system over internal documents needs:

  • Retrieval-time filtering by the requester's permissions (never retrieve, let alone show, a document the user isn't cleared to see — filtering after generation is too late).
  • Data classification tags on each chunk's payload, enforced at query time via Qdrant payload filters.
  • Audit logging of every query, retrieved context, and answer — the notebook's production_logs list is the seed of this, but a real system persists it outside the process.

def dense_retrieve(query, top_k=5):
    qv = embedding_model.encode(query, normalize_embeddings=True).tolist()
    hits = qdrant_client.query_points(collection_name="lab", query=qv, limit=top_k, with_payload=True).points
    return [{"id": h.payload["doc_id"], "text": h.payload["text"]} for h in hits]

def bm25_retrieve(query, top_k=5):
    scores = bm25.get_scores(tokenize(query))
    idx = np.argsort(scores)[::-1][:top_k]
    return [{"id": documents[i]["id"], "text": documents[i]["text"]} for i in idx]

def hybrid_retrieve(query, k=60, top_k=8):
    dense, lex = dense_retrieve(query), bm25_retrieve(query)
    scores = {}
    for rank, item in enumerate(dense, 1): scores[item["id"]] = scores.get(item["id"], 0) + 1/(k+rank)
    for rank, item in enumerate(lex, 1): scores[item["id"]] = scores.get(item["id"], 0) + 1/(k+rank)
    ranked = sorted(scores, key=scores.get, reverse=True)[:top_k]
    return [doc_by_id[d] for d in ranked]

Program 6 — Self-RAG critique loop (Tab ⑦)
def critique_answer(question, answer, contexts):
    prompt = f"Question: {question}\nAnswer: {answer}\nContext:\n{''.join(contexts)}\nReturn PASS or RETRY only."
    result = call_llm("You are a strict RAG quality checker.", prompt)
    return "PASS" if "PASS" in result.upper() else "RETRY"

def self_rag(question):
    query = question
    for attempt in range(2):
        candidates = hybrid_retrieve(query)
        reranked = cohere_rerank(query, candidates)
        contexts = [c["text"] for c in reranked]
        answer = generate_rag_answer(question, contexts)
        if critique_answer(question, answer, contexts) == "PASS":
            return {"answer": answer, "retrieval": reranked, "attempts": attempt + 1}
        query = call_llm("Rewrite this query for better retrieval.", question)
    return {"answer": answer, "retrieval": reranked, "attempts": 2}

Q1What is the actual difference between dense retrieval and keyword (BM25) retrieval, and why does a production system usually need both?
💡 Hint: What to cover in your answer
  • Explain WHAT each method scores on (meaning vs. exact token overlap)
  • Give a concrete example of a query where each one wins and the other loses
  • Mention that embeddings are weak on rare exact tokens like codes/IDs
  • Name the fusion technique that combines them
✅ Model Answer

Dense retrieval encodes text into vectors that capture meaning, so it can match "how much time off do I get" to "annual leave policy" even though they share no words. BM25 instead scores exact token overlap, weighted by term rarity, so it has no idea about meaning but is excellent at exact matches like error codes or product IDs that an embedding model was never trained to treat as meaningful units. A production system needs both because real user queries mix both styles — sometimes paraphrased, sometimes copy-pasting an exact code from an error message — and either method alone silently fails on the other's strength. I combine their two ranked lists with Reciprocal Rank Fusion rather than trying to average their raw scores, since cosine similarity and BM25 scores live on incomparable scales.

Q2Why does a RAG system need reranking at all if hybrid search already produces a ranked list?
💡 Hint: What to cover in your answer
  • Explain the cost/precision trade-off between fast retrieval and reranking
  • Describe the "cheap-then-precise" two-stage pattern
  • Mention why you wouldn't rerank the entire corpus
✅ Model Answer

Hybrid search is built to scan the whole corpus cheaply and fast, which means it's necessarily an approximation — it can't afford to deeply analyze every query/document pair. A reranker is a model trained specifically for precise query-document relevance scoring, but it's too slow and expensive to run against thousands of documents, so it only ever scores the small shortlist hybrid search already narrowed down. This cheap-then-precise two-stage pattern is standard in production search generally, not just RAG: you trade a little extra latency on a small shortlist for a meaningful precision gain, instead of paying that cost on the whole corpus.

Understanding of why retrieval and reranking are different tools solving different constraints, not redundant steps.

Q3Explain the difference between what Self-RAG checks and what CRAG checks.
💡 Hint: What to cover in your answer
  • State precisely what each pattern evaluates (answer quality vs. retrieval/evidence quality)
  • Explain why checking the answer alone isn't sufficient
  • Mention that CRAG can route to a tool or a fallback, not just retry
✅ Model Answer

Self-RAG asks "is the generated answer good enough?" — it critiques the output after generation and, if the critique fails, rewrites the query and tries the whole retrieve-rerank-generate pipeline again, within a capped retry budget. CRAG asks an earlier and different question: "is the retrieved evidence itself reliable enough to trust?" — using something like the top rerank score as a confidence signal, before fully committing to generation on top of it. The key difference is that CRAG has three possible outcomes instead of two: trust the evidence and proceed, redirect to an external tool if one fits the question, or return an explicit "I don't know" safe fallback. Self-RAG alone can still confidently hallucinate on bad evidence if the critique step itself is fooled; CRAG catches that earlier, at the evidence-quality layer.

🎯 What's being tested

Whether the candidate understands these are checks at two different pipeline stages, not two names for the same idea.

  • Doesn't mention CRAG's tool/fallback branching

Q4Why is Reciprocal Rank Fusion used instead of just averaging normalized scores from each retriever?
💡 Hint: What to cover in your answer
  • Explain what makes raw scores from different retrievers incomparable
  • Describe what RRF actually uses instead of raw scores
  • Mention the role of the rrf_k constant
✅ Model Answer

A cosine similarity score and a BM25 score are computed by entirely different formulas on different scales that shift with corpus size and model choice, so even after min-max normalizing them, averaging them mixes two numbers that don't mean the same thing. RRF sidesteps this by discarding the raw scores entirely and using only each document's rank position in each list — a document scores 1/(k+rank) per list it appears in, and those are summed across lists. Rank position is directly comparable across any two retrieval methods, which is the whole reason it's the fusion target instead of the score. The constant k (60 is a common default) controls how much rank-1 dominates versus how flat the blend is, and it's a real tuning parameter, not a fixed constant.

🎯 What's being tested

Understanding of why score-space fusion is unreliable and rank-space fusion solves that specific problem.

Q5What's the difference between a guardrail and a CRAG safe-fallback? Aren't they both "the system refusing to answer"?
💡 Hint: What to cover in your answer
  • Explain WHEN each one runs in the pipeline (before vs. after retrieval)
  • Explain WHAT each one is protecting against
  • Give an example question that triggers each one
✅ Model Answer

A guardrail runs before retrieval even happens — it's a cheap check on the question itself, meant to reject requests that are disallowed regardless of what's in the knowledge base, like asking the system to reveal credentials. A CRAG safe-fallback runs after retrieval and reranking, and it's not about the question being disallowed — it's about the system having looked for an answer, found nothing reliable, and admitting that honestly instead of guessing. The first protects against misuse; the second protects against confident wrongness on a legitimate question the knowledge base simply doesn't cover. Conflating them would mean either running expensive retrieval on requests that should have been rejected instantly, or rejecting legitimate questions as if they were malicious.

Q7What does "grounding" mean in a RAG prompt, and what specifically in the prompt enforces it?
💡 Hint: What to cover in your answer
  • Define grounding precisely
  • Name the concrete prompt elements that enforce it
  • Explain what happens if grounding instructions are dropped
✅ Model Answer

Grounding means the model's answer is constrained to only use information present in the retrieved context, rather than falling back on its own training-data knowledge or inventing plausible-sounding claims. In practice this is enforced by an explicit instruction in the prompt — "answer using only the retrieved context" — combined with an explicit escape hatch instructing the model to say the documents don't provide enough information rather than guess, and usually a temperature of 0 to minimize creative drift. If you drop those instructions, the model will often still produce a fluent answer, but it may blend in outside knowledge indistinguishably from the retrieved facts, which is much harder to catch than an obviously wrong answer.

Q8Why does RAGAS need an LLM to judge the answers — isn't that circular, using an LLM to grade an LLM?
💡 Hint: What to cover in your answer

  • Address the circularity concern directly — what makes it less circular in practice
  • Mention the role of a separate judge model vs. the generation model
✅ Model Answer

Metrics like faithfulness and answer relevancy require a judgment call — "is this specific claim actually supported by this specific context" isn't something a string-match or keyword-overlap check can reliably determine, because the same fact can be phrased many different ways. So RAGAS uses a separate judge LLM call, scoring against a fixed rubric, to make that judgment. It's not perfect, but it's far better than having no measurement at all.
