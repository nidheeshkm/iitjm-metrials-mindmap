Regression metrics: MAE and R²

Used when the target is a number, e.g. predicting how many pages a batch will fail on.

MAE = mean(|y_true − y_pred|) → "on average I'm off by N pages" R² = 1 − Σ(y_true − y_pred)² / Σ(y_true − mean(y_true))² 1.0 = perfect · 0 = no better than predicting the mean · <0 = worse than the mean

Certain Neither has a direct Ragas metric. Ragas scores are bounded 0–1 per row and nobody regresses them. Likely The one place MAE earns its keep in RAG work is tab ⑩: measuring how far an LLM judge's scores sit from human scores (judge MAE of 0.05 is good; 0.25 means the judge is noise). R² has essentially no practical use here, so this guide stops at the definition.

ROC and AUC

Many models output a probability, and you choose a threshold to turn it into yes/no. The ROC curve plots recall (true positive rate) against false positive rate at every possible threshold. AUC is the area under it.

Where it returns in this guide: a Ragas score is a continuous number, and production gates turn it into pass/fail. When you collect human "this answer is wrong" labels and check how well faithfulness separates good from bad answers, that is an ROC/AUC analysis. It tells you whether a threshold like faithfulness ≥ 0.8 means anything (tab ⑩).

Runnable: all of the above in 25 lines (scikit-learn)
from sklearn.datasets import make_classification, make_regression
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression, LinearRegression
from sklearn.metrics import (accuracy_score, precision_score, recall_score, f1_score,
                             roc_auc_score, mean_absolute_error, r2_score, confusion_matrix)

# Imbalanced on purpose (~20% positives) so accuracy looks better than it should
X, y = make_classification(n_samples=1000, weights=[0.8], random_state=42)
# stratify=y keeps the 80/20 ratio in both splits; without it a small test set can be skewed
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.2, stratify=y, random_state=42)

clf = LogisticRegression(max_iter=1000).fit(X_train, y_train)   # learn ONLY from train
y_pred = clf.predict(X_test)                                     # hard 0/1 at threshold 0.5
y_prob = clf.predict_proba(X_test)[:, 1]                         # probabilities, needed for ROC

print(confusion_matrix(y_test, y_pred))
print("accuracy ", accuracy_score(y_test, y_pred))
print("precision", precision_score(y_test, y_pred))
print("recall   ", recall_score(y_test, y_pred))
print("f1       ", f1_score(y_test, y_pred))
print("roc_auc  ", roc_auc_score(y_test, y_prob))   # uses probabilities, not hard labels

# Regression counterpart
Xr, yr = make_regression(n_samples=500, noise=20, random_state=0)
Xr_tr, Xr_te, yr_tr, yr_te = train_test_split(Xr, yr, test_size=0.2, random_state=0)
reg = LinearRegression().fit(Xr_tr, yr_tr)
print("MAE", mean_absolute_error(yr_te, reg.predict(Xr_te)), " R2", r2_score(yr_te, reg.predict(Xr_te)))

② Embeddings & retrieval

The notebook builds its retriever in four lines and evaluates it later with Semantic Similarity and Answer Relevancy. Both metrics run on the same machinery: turn text into vectors and measure angles.

What an embedding is

An embedding model maps a sentence to a fixed list of numbers. all-MiniLM-L6-v2 outputs 384 numbers per sentence Certain, which is why the notebook prints Embedding shape: (20, 384) for its 20 audit documents. Sentences with similar meaning land near each other in this 384-dimensional space.

Analogy: the libraryA librarian doesn't shelve books alphabetically by title; they shelve by subject, so "OCR scanner failures" and "document digitisation errors" sit on the same shelf even though they share no words. An embedding gives every sentence a shelf address. Retrieval means walking to the shelf nearest your question.

Cosine similarity and why the notebook normalizes

cosine(a, b) = (a · b) / (‖a‖ × ‖b‖) if ‖a‖ = ‖b‖ = 1 (normalized) → cosine(a, b) = a · b

The notebook's comment says the dot product is "effectively cosine similarity". It is exactly cosine similarity, because both sides were encoded with normalize_embeddings=True Certain. That lets document_embeddings @ question_embedding score all 20 documents in one matrix multiply.

⚠️ Common Mistake: normalizing one side onlyIf documents are normalized but the query isn't (or vice versa), dot-product scores scale with the query's length. The ranking for a single query is unchanged, but any score threshold ("drop chunks below 0.4") becomes meaningless across queries. Normalize both or call a true cosine function.

The 3 W's

WhatRagas is an open-source Python library of evaluation metrics for RAG and LLM apps. Each metric takes some combination of user_input, response, retrieved_contexts and reference, and returns a score, usually 0–1. Some metrics are deterministic; most of the important ones call an LLM judge with metric-specific prompts.
WhyFree-text answers can't be graded with == (tab ⓪). Writing your own judge prompt per criterion is possible (tab ⑥) but you'd be re-inventing claim decomposition, verdict parsing and scoring formulas. Ragas gives standardized, published definitions, so "faithfulness 0.82" means the same thing across teams and runs.
When Offline, before shipping: compare retrievers, chunk sizes, prompts and models on a golden set. This is the notebook's use.
In CI: a regression gate on every prompt or index change (tab ⑪).
Online, sampled: reference-free metrics (faithfulness, answer relevancy) on a small share of live traffic, because live traffic has no ground truth.
Not when: the output is fully structured (use exact checks), or you need a legal-grade verdict (use humans; Ragas is a screening tool).

The lesson in one line: lexical metrics give wrong answers with near-identical wording higher scores than right answers with different wording. They measure surface form, not truth. And BLEU scores a perfect one-word match as 0.

1. Semantic Similarity 📘 LLM nb

Measures: cosine similarity between the embeddings of reference and response (tab ②). Catches: paraphrases ("15%" vs "fifteen percent"). Misses: numbers and negations. Embeddings place "15%" and "16%" very close, and "is approved" vs "is not approved" are often close too.

semantic_similarity = cos(embed(reference), embed(response)) # optional threshold → 0/1
⚠️ Common Mistake: treating 0.85 semantic similarity as "85% correct"It's an angle between vectors, not a proportion of correctness. MiniLM similarity between two unrelated English sentences often sits around 0.1–0.3, not 0, so the usable range is compressed. Calibrate against examples you've labelled before picking a threshold.

2. ROUGE-L 📘 LLM nb

Measures: the longest common subsequence (LCS) of words: shared words in the same order, gaps allowed. Ragas defaults to rouge_type="rougeL", mode="fmeasure" Certain.

P = LCS / words(response) R = LCS / words(reference) ROUGE-L F = 2PR / (P + R)

Row 0 worked: the reference "the ocr failure rate is 15" (6 tokens) and the 13-token response share the subsequence "ocr failure rate" (3 tokens). Likely P = 3/13, R = 3/6, F ≈ 0.316, matching the notebook output exactly. The verbose answer is penalized through precision.

Also note: ROUGE scored "predicts" vs "predicted" as 1.0 because the scorer uses stemming, and it lowercases ("Approved" = "approved").

3. String similarity (Levenshtein) 📘 LLM nb

score = 1 − levenshtein_distance(ref, resp) / max(len(ref), len(resp))

Edit distance counts single-character inserts, deletes and substitutions. "15%" → "16%" is one edit in 24 characters, so 0.96, while the answer is factually wrong. Ragas also offers HAMMING, JARO and JARO_WINKLER via DistanceMeasure.

Analogy: the spell-checkerA spell-checker would say "16%" is a perfect spelling of a number. That's all Levenshtein knows. Use it for IDs, codes and names where typos matter, never for factual answers.

4. BLEU 📘 ADD nb

BLEU = BP × exp( Σ_{n=1..4} ¼ · log p_n ) p_n = clipped n-gram precision BP = brevity penalty = min(1, e^(1 − ref_len/resp_len))

BLEU is a geometric mean of 1- to 4-gram precisions. If the response has no matching 4-gram, one factor is 0 and the whole product collapses to 0. That's why "Paris" vs "Paris" scores 0.00 Certain. BLEU was designed for corpus-level machine translation, where thousands of sentences smooth this out.

⚠️ Notebook Enhancement: BLEU on short answersThe additional-metrics notebook demonstrates BLEU on a sentence identical to its reference (score 1.0), which hides the failure. Add a one-word example to show the collapse, and prefer CHRF or ROUGE for short RAG answers.

5. CHRF 📘 ADD nb

Character n-gram F-score (default n up to 6, with recall weighted higher). It tolerates inflection ("predicts"/"predicted" = 0.84) and casing changes better than BLEU, and it doesn't collapse to 0 on short strings. A good cheap default when you need one lexical metric.

Context Precision

For each retrieved chunk in rank order, the LLM judges whether it was useful for producing the reference answer (vₖ = 1 or 0). The score is average precision:

context_precision = Σ_k ( precision@k × v_k ) / (number of useful chunks) precision@k = useful chunks in top k / k
⚠️ Common Mistake: reading context precision as "fraction of chunks that were useful"The notebook's own comment says "how many were actually useful/relevant", which describes plain precision. In fact chunks ranked after the last useful one don't lower the score, so [useful, noise ×9] still scores 1.0. Those 9 noise chunks can still hurt the generator; that's what Noise Sensitivity measures (tab ⑧).

context_recall = |reference statements attributable to retrieved_contexts| / |reference statements|

It decomposes the reference (not the response) into statements and checks each against the retrieved chunks. Every notebook question has a one-statement reference, so recall can only be 0 or 1. A multi-hop golden set is needed for this metric to say anything nuanced (🛠 C2).

The practical rule: report a bootstrap confidence interval with every average (Program 7), and don't call a change a regression unless the intervals separate, or a paired test on the same rows says so.

If faithfulness on one row swings 0.67 → 1.0 between runs, single-run comparisons are noise. Track per-row standard deviation and average over repeats for decisions that matter.

def retrieve(question, top_k=TOP_K):
    q = model.encode([question], normalize_embeddings=True)[0]
    scores = document_embeddings @ q                      # 20 cosine scores in one matmul
    top = np.argsort(scores)[::-1][:top_k]                # highest first
    # 🛠 C3: return the document ID alongside the text, so evaluation can match on IDs
    return [{"doc_id": int(i), "text": audit_data[i], "score": float(scores[i])} for i in top]

def hit_at_k(gold_ids, retrieved_ids, k=TOP_K):
    # 1.0 if ANY gold doc is in the top k. For multi-hop rows also report recall below.
    return float(any(g in retrieved_ids[:k] for g in gold_ids))

def mrr(gold_ids, retrieved_ids):
    # Rank-aware: gold doc at rank 1 → 1.0, rank 3 → 0.33, missing → 0
    for rank, d in enumerate(retrieved_ids, start=1):
        if d in gold_ids:
            return 1.0 / rank
    return 0.0

def id_recall(gold_ids, retrieved_ids):
    # Fraction of required gold docs retrieved: matters for multi-hop questions
    return sum(g in retrieved_ids for g in gold_ids) / len(gold_ids) if gold_ids else float("nan")

import asyncio, hashlib, json, random, time, datetime as dt

CACHE_PATH = "ragas_cache.json"
try:
    CACHE = json.load(open(CACHE_PATH))
except FileNotFoundError:
    CACHE = {}

RUN_META = {"ragas": ragas.__version__, "judge": JUDGE_MODEL, "generator": GEN_MODEL,
            "eval_embed": EVAL_EMBED_MODEL, "top_k": TOP_K,
            "started": dt.datetime.utcnow().isoformat() + "Z"}

def cache_key(metric_name, kwargs):
    # Judge model and ragas version are part of the key: a new judge must never reuse old scores
    blob = json.dumps({"m": metric_name, "k": kwargs, "j": RUN_META["judge"], "v": RUN_META["ragas"]},
                      sort_keys=True, default=str)
    return hashlib.sha256(blob.encode()).hexdigest()

SEM = asyncio.Semaphore(16)
STATS = {"calls": 0, "cache_hits": 0, "failures": 0}

async def score_cached(name, metric, kwargs, retries=4, timeout=120):
    key = cache_key(name, kwargs)
    if key in CACHE:
        STATS["cache_hits"] += 1
        return CACHE[key]
    for attempt in range(retries):
        try:
            async with SEM:
                STATS["calls"] += 1
                value = (await asyncio.wait_for(metric.ascore(**kwargs), timeout=timeout)).value
            CACHE[key] = value
            return value
        except Exception as e:
            if attempt == retries - 1:
                STATS["failures"] += 1
                return float("nan")
            await asyncio.sleep(min(30, 2 ** attempt) + random.random())   # backoff + jitter

async def evaluate(rows, metrics=METRICS, repeats=1):
    async def one(row, rep):
        names = list(metrics)
        vals = await asyncio.gather(*(score_cached(f"{n}#r{rep}", metrics[n][0], metrics[n][1](row)) for n in names))
        return {"qid": row["qid"], "type": row["type"], "rep": rep, **dict(zip(names, vals))}
    t0 = time.time()
    out = await asyncio.gather(*(one(r, k) for r in rows for k in range(repeats)))
    json.dump(CACHE, open(CACHE_PATH, "w"))
    print(f"{len(out)} row-runs in {time.time()-t0:.1f}s · {STATS}")
    return pd.DataFrame(out)

def bootstrap_ci(values, n_boot=2000, alpha=0.05, seed=0):
    v = np.asarray([x for x in values if not np.isnan(x)])
    if len(v) == 0:
        return (np.nan, np.nan, np.nan)
    rng = np.random.default_rng(seed)
    means = rng.choice(v, size=(n_boot, len(v)), replace=True).mean(axis=1)
    return (v.mean(), np.quantile(means, alpha / 2), np.quantile(means, 1 - alpha / 2))

LOWER_IS_BETTER = {"noise_irrelevant"}

def summarize(df):
    per_row = df.groupby("qid").mean(numeric_only=True)          # average repeats first

    return pd.DataFrame(rows).set_index("metric")

20. Ragas scores for the same rows vary by about ±0.08 between runs, and some runs fail with 429 errors midway, losing everything. Fix both problems.Debugging

💡 Hint
  • Stochastic decomposition/verdicts
  • Repeats and averaging, CIs
  • Bounded concurrency
  • Backoff + jitter, timeouts
  • Incremental persistence + cache, NaN policy
✅ Model answer

Variance comes from the LLM judge. Even at temperature 0, claim decomposition and verdicts differ between calls, and providers may route to different backends. I'd pin the judge model version, run two or three repeats for decisions that matter, average per row, and report bootstrap CIs and per-row standard deviation, so I stop treating a ±0.08 swing as signal. 21. A row has Context Hit = 0 but Context Recall = 1.0, and the answer is correct. Which do you trust, and what's wrong?Debugging

  • Chunking differences
  • IDs instead of text
  • Recall checks claims, not strings
  • Both have roles
✅ Model answer

I'd trust context recall here and fix context hit. The notebook's context hit is ground_truth_context in contexts, which is exact string equality against list items. If the corpus was re-chunked, whitespace changed, or the retrieved chunk contains the gold sentence plus neighbouring text, the check fails even though the information was retrieved. 23. Design online quality monitoring for a production RAG service, using SRE practices.System design

💡 Hint
  • Async sampled scoring off request path
  • Reference-free SLIs
  • SLOs, burn-rate alerts
  • Human review loop
  • Drift detection for judge and data
✅ Model answer

Each request logs question, retrieved chunk IDs and scores, answer, model versions and latency to an event stream, with PII redacted before anything goes to a third-party judge. A consumer samples 1–2%, stratified by intent and tenant, and scores asynchronously with faithfulness and answer relevancy, the reference-free metrics. Cheap signals are computed on 100% of traffic: empty-retrieval rate, top-1 similarity distribution, "not found" rate, and answer length. Low-scoring answers go to a review queue; confirmed failures get references and join the CI golden set. A fixed calibration set is re-scored weekly to detect judge drift. This mirrors synthetic monitoring: the golden-set run against production is a probe, and live scoring is the SLI.

24. Design a program to validate and maintain trust in your LLM judges (Ragas and custom) over time.System design

💡 Hint
  • Human-labelled calibration set
  • AUC, κ, MAE
  • Threshold from ROC
  • Re-validate on version change
  • Bias checks
✅ Model answer

I'd build a calibration set of 200 rows, stratified to include clear passes, clear failures and borderline cases, deliberately including hallucinations and distractor-copied answers. Two humans label each row per criterion (faithful 0/1, correct 0/1) with an adjudication step, and I measure inter-annotator κ first, because if humans don't agree, no judge can. For each metric I compute AUC against the human binary label, Cohen's κ at the chosen threshold, and MAE where humans gave graded scores. Thresholds come from the ROC operating point that matches the business cost of false passes versus false fails. Bias probes: swap answer order for pairwise judgments, pad correct answers with irrelevant text to test verbosity bias, and score generator-family outputs with same-family and different-family judges to test self-preference. Governance: judge model, prompt and ragas version are pinned and recorded with every score. Any change re-runs the calibration set, and a judge that drops below the AUC bar can't gate releases. The calibration set gets 20–30 new rows a quarter from production failures, so it tracks the real distribution.
